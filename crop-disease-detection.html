Crop disease detection — offline-first, on-device

An app that helps farmers diagnose and treat crop disease, built for low-connectivity fields, not clean lab conditions.

Problem

Farmers who already suspect something's wrong with a plant have no fast, reliable way to get an accurate answer. Common practice is comparing notes with other farmers who've seen something similar — slow, informal, and often wrong.

Decision

Optimized for reliability in the field over lab-benchmark accuracy: on-device inference (MobileNetV2, TFLite, offline-first) instead of a cloud-only model, so a diagnosis doesn't depend on a signal. That trades peak accuracy and easy model updates for something farmers can actually use every day, no connection required.

While reviewing my own design, I caught a flaw: my pipeline let any expert-verified case flow straight into the retraining dataset, on the assumption that "diagnosis correct" meant "good training example." It doesn't. An agronomist can correctly diagnose Late Blight from a dark, blurry photo using experience and context — the diagnosis is right, but the image is a poor training sample: low resolution, maybe duplicated, missing the features the model needs to learn from. Feeding every verified case into training would have slowly contaminated the dataset. I split the flow into two separate questions — is the diagnosis correct, and separately, is this image worth training on — and added a second approval step for the second question.

Outcome

Avoided a specific failure mode — dataset contamination — before any code existed to cause it. The project is currently at repo-scaffold-and-decision-log stage: a real architecture decision record, no dataset or model code yet.
